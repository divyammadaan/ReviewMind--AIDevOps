The decisive comparison

Defects created by deleting correct code leak their own answer: the removed lines state the contract being violated, and the diff-only arm simply reads it off. Only addition-mode defects — which delete nothing — test retrieval honestly.

Three times our own experiment misled us

“RAG is worse” was a network artifact The first run showed retrieval losing, 80% vs 100%. Two API calls had returned HTTP 429. A failed call yields zero issues, which the scorer correctly counted as misses. The heaviest arm throttles first — the bias ran against our own method.
The dataset leaked its own answers With that fixed, both arms tied at 100%. The diff-only arm was solving cross-file defects it shouldn't have seen, because every defect was made by deleting correct code — and the deleted lines state the violated contract.
The metric scored location, not understanding Credit went to any issue within ±3 lines, so the diff-only arm scored by flagging the right line while diagnosing the wrong bug. A concept rubric separated the arms 50% vs 100%.

Limitations — stated plainly

  • n = {{ llm_rag.n_cases }} overall, n = 4 in the decisive cell. CIs are wide and overlapping.
  • Synthetic defects are likely more stereotyped than real ones. Only the between-arm comparison is defensible.
  • One model, one provider, one language, one repository.
  • Precision is a lower bound — an unseeded but genuine finding counts against us.
  • The embedding retriever is implemented but unmeasured.
  • We authored both the system and its evaluation. Three defect classes were chosen for static analysis to win; it scores 3/3 on them.
