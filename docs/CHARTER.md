# ReviewMind — Project Charter / Synopsis

**Project:** ReviewMind — Semantic AI Code Reviewer for GitHub
**Course:** CSE 4011 — Intelligent Developer Tools and AI DevOps Workflows
**Phase:** A2 (Mid-Term), 5–9 Oct 2026 · *revised from the A1 synopsis*

---

## 1. Problem Definition

Code review catches bugs, security flaws and missing error handling before merge,
but it is slow, inconsistent and gated on reviewer availability. Small teams and
student projects often skip it, letting preventable defects reach production.

Automated linters partly fill the gap, but only for defects expressible as
patterns. They cannot judge whether a change is *semantically* wrong — whether
it breaks a contract its callers depend on, or dereferences a value that may be
`None` because of a function defined in another file.

## 2. Research Question

> Does supplying an LLM with **repository-wide retrieved context** measurably
> improve its ability to detect real defects, compared with (a) the diff alone,
> and (b) conventional static analysis?

| ID | Sub-question | Comparison |
|----|---|---|
| RQ1 | Does an LLM detect more seeded defects than static analysis? | Arm A vs B |
| RQ2 | Does repository-wide retrieval improve on diff-only review? | Arm B vs C |
| RQ3 | What does retrieval cost per unit of detection gained? | Arm B vs C |

**Revision note.** The A1 synopsis stated a *build* objective with no research
question, baseline or metrics. The faculty mid-term criteria are research
criteria, so an experimental layer was added. This is an explicit change of
scope, documented in `docs/RESEARCH_DESIGN.md` §8.

## 4. Methodology

1. **Corpus** — a small Python application with genuine cross-file dependencies.
2. **Defect injection** — 14 labelled defects across 7 classes, generated by
   script. Ground truth is exact (file + line span + class).
   - 10 *deletion-mode* (remove correct code)
   - 4 *addition-mode* (add wrong code, leaking nothing)
3. **Three arms** on identical data, scored by one scorer:
   - **A** `static` — ruff + bandit (non-AI baseline)
   - **B** `llm_diff` — LLM, diff only
   - **C** `llm_rag` — LLM + retrieved repository context
4. **Metrics** — positional recall, **semantic** recall (did the report describe
   the *actual* defect?), precision lower bound, Wilson 95% CIs, tokens, latency.
5. **Controls** — arms B and C share one prompt builder, model and temperature;
   only the context differs, by construction.

## 5. Key Results (run `run_20261004T105129Z`, `openai/gpt-oss-120b`)

| Arm | Positional recall | **Semantic recall** | Tokens/case |
|---|---|---|---|
| static | 28.6% | 21.4% | 0 |
| llm_diff | 92.9% | 78.6% | 1,500 |
| llm_rag | **100%** | **100%** | 2,219 |

On the only valid test bed for RQ2 (addition-mode, semantic scoring):
**static 0/4 · diff-only 2/4 · RAG 4/4.**

| Cost | ₹0 | ₹0 |

**Risks encountered and mitigated** (detail in `docs/TOOL_COVERAGE.md`):
Groq retired Llama 3.3 → substituted `gpt-oss-120b`; Sourcegraph is amd64-only →
public instance + Mac host; `cover-agent` needs Python <3.14 → containerised;
Sweep.dev service shut down → capability reimplemented; rate limits were
corrupting results → token-budget throttle.

## 7. Scope Boundaries

**In scope:** static analysis of diffs, retrieval, review generation, test
suggestion, PR commenting, CI automation, the three-arm experiment.

**Out of scope, deliberately:** executing pull-request code (a safety property,
not an omission); auto-merging; languages other than Python; claims about LLMs
in general.
